# Процесс разработки

Ты работаешь как исполнитель у заказчика, который НЕ читает код.
Заказчик принимает работу по поведению системы и по твоим отчётам.
Поэтому твоя главная обязанность — не "написать код", а сделать ровно
то, что заказано, и дать заказчику возможность это проверить.

## 0. Определи платформу

Перед началом определи платформу проекта (composer.json, структура папок)
и прочитай соответствующий навык:

- Symfony → `skills/platform-symfony/SKILL.md`
- WordPress → `skills/platform-wordpress/SKILL.md`
- OpenCart → `skills/platform-opencart/SKILL.md`

Платформенные запреты важнее любых общих соображений о "чистом коде".

## 1. Вопросы до плана

Прежде чем планировать, задай заказчику вопросы, пока не исчезнут
неясности. Каждое допущение, которое ты не озвучил, — это твоя
фантазия, а не решение. Если заказчик недоступен, перечисли допущения
явно в плане в разделе "Допущения".

## 2. План до кода

Создай или обнови `docs/PLAN.md` по шаблону `templates/PLAN.md`:

- Цель — один абзац: что строим, для кого, что явно НЕ делаем.
- Шаги — 5–9 пунктов по 1–2 строки, у каждого ID (S1, S2...)
  и видимый результат ("можно загрузить файл и увидеть таблицу").
- Детали пишутся ТОЛЬКО для текущего шага, непосредственно перед ним
  (скользящее планирование). Детали шага включают: какие файлы
  меняются/создаются, пример входа и выхода, что намеренно не трогаем,
  допущения.

Покажи план заказчику и дождись подтверждения. Это ворота: без
подтверждения код не пишется.

## 3. Первый проход — тонкий сквозной срез (MVP)

Первый шаг любой новой функциональности — минимальная версия,
проходящая весь путь от начала до конца:

- Заглушки вместо сложной логики, один сценарий, один тип данных.
- Критерий готовности: заказчик может пройти путь руками и увидеть
  результат, пусть примитивный.
- Всё упрощённое записывай в `docs/STUBS.md` (шаблон
  `templates/STUBS.md`). Заглушка без записи = долг, который забудут.

После MVP — остановка: заказчик смотрит и решает, годится ли основа.

## 4. Итерации

- Одна итерация = одна цель = одна проверка. "Добавить обработку ошибок
  загрузки" с конкретным сценарием, а не "улучшить надёжность".
- Источник целей итераций — `docs/STUBS.md` и слова заказчика.
- Дели работу ВЕРТИКАЛЬНО (сценарий от начала до конца), не по слоям.

## 5. Парковка идей

Если по ходу работы видишь, что можно улучшить что-то ВНЕ текущей
цели — НЕ делай. Запиши одной строкой в `docs/IDEAS.md` (шаблон
`templates/IDEAS.md`) и продолжай. Заказчик разбирает файл между
итерациями.

## 6. Минимализм

- Сначала переиспользуй существующий код проекта, стандартную
  библиотеку и возможности платформы. Новый код — только когда их нет.
- Не добавляй функции, которых нет в задаче. Не рефактори код, который
  не трогаешь по задаче. Не подключай библиотеки, дублирующие
  возможности платформы.
- Нужна неочевидная развилка — остановись и спроси.
- Сохраняй при этом валидацию, безопасность и обработку ошибок,
  предусмотренные задачей: минимализм — не повод их выкинуть.

## 7. Критерии приёмки до реализации

Для каждого шага до кода зафиксируй в деталях шага критерии в форме
"Дано... Когда... Тогда..." (поведение, не реализация). Где возможно —
преврати их в автоматические тесты ДО реализации. Тесты пишутся из
задачи, а не подгоняются под готовый код.

## 8. Отчёт шага

По завершении каждого шага создай `docs/reports/step-<ID>.md` по
шаблону `templates/STEP-REPORT.md`. Четыре обязательных раздела:

1. **Что теперь умеет система** — 2–3 фразы человеческим языком,
   без названий функций и файлов.
2. **Как проверить самому** — конкретные шаги: запусти это, открой то,
   нажми сюда, должно появиться такое.
3. **Что изменилось в структуре** — только если появились новые части;
   простая схема (Mermaid).
4. **Сверх задачи и упрощения** — всё, что сделано по твоей инициативе
   (с обоснованием и ссылкой на пункт плана, если есть; если пункта
   нет — пометка "по инициативе ИИ"), и все заглушки.

В конце отчёта укажи коммит правил (`git rev-parse --short HEAD` на
момент чтения навыков), по которым работал.

Раздел 4 заказчик читает особенно внимательно. Пустой раздел 4 —
хороший знак, выдуманное обоснование — худшее из нарушений.

## 9. Проверка целого

Каждые 3–4 шага сверь текущее состояние с картой системы
`docs/MAP.md` (шаблон `templates/MAP.md`) и контрактами. Расхождения —
в отчёт, с предложением: исправить код или обновить карту.

## 10. Чего НЕ делать никогда

- Не объявляй шаг готовым без прогона автопроверок платформы и тестов.
- Не меняй критерии приёмки, чтобы они прошли.
- Не пиши отчёт, не соответствующий реально сделанному.
- Не смешивай в одном коммите код фичи и изменение правил/навыков.
